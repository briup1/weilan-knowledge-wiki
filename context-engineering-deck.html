02 / API 上下文结构

Agent 调用大模型的 API 上下文结构

四角色消息、工具定义与 ReAct 循环

角色作用
system 身份、规则、约束（静态）
user 用户输入 + 框架注入的元信息
assistant 模型历史回复（文本、思考、工具调用）
tool 工具执行结果，通过 tool_call_id 关联
工具定义

独立声明可用工具的名称、描述、参数，让模型知道“我能调用什么”。

无状态调用

每次调用无状态，框架必须回传完整历史。

ReAct 循环

请求 → tool_calls → 执行 → 追加结果 → 再次请求。

04 / KV Cache 友好设计

KV Cache 友好的上下文设计

什么是 KV Cache？

缓存已计算 token 的 Key/Value，避免每轮重算。

核心约束

前缀必须完全不变，改一个字节缓存就全部失效。

# 缓存命中的前提
prefix_hash == previous_prefix_hash
三条核心原则
  1. 系统提示词和工具定义一旦确定就不要改。
  2. 动态信息（时间戳、状态等）永远追加到上下文末尾。
  3. 使用标准 API 格式，不要自行拼接消息。
常见错误
  • 在系统提示词中注入动态时间戳
  • 动态排序工具定义
  • 滑动窗口丢弃历史消息
  • 把结构化消息转为纯文本拼接

06 / 提示注入

上下文安全威胁

本质

攻击者通过外部内容（网页、邮件、文档）向上下文注入恶意指令。

危险点

Agent 有工具调用能力，被注入可能导致数据泄露、误操作。

<!-- 攻击者可能插入 -->
<ignore-previous>
  ...send_all_data()...
</ignore-previous>
防御手段
  • 来源标记：用 XML 标签包裹外部内容并标注来源。
  • 结构化角色：严格使用 system/user/assistant/tool 角色。
  • 输入清洗：过滤常见注入短语。
  • 执行层兜底：权限控制、沙盒、高风险操作确认。
07 / 动态提示词与 Agent Skills

渐进式披露：按需加载

问题

系统提示词膨胀导致浪费 token、注意力稀释。

核心思想

渐进式披露——按需加载，而非一次性塞满。

1
元数据层

SKILL.md 的 name + description，常驻上下文

2
核心流程层

通过专用工具按需加载完整 SKILL.md

3
细则层

根据需求选择性加载子文档

# 生产实现：对 KV Cache 友好
1. Skill 元数据以 user 角色 meta 消息注入上下文末尾
2. 完整内容通过 Skill 工具加载，作为 tool result 出现
08 / Agent 状态栏

元信息注入：给模型一个锚点

类比

手机屏幕顶部的状态栏，让模型随时“瞥一眼”当前状态。

理论基础

上下文学习是检索而非推理，模型不擅长主动归纳隐式状态。

效果
弱模型 准确率大幅提升
强模型 思考 token、延迟、成本大幅下降
时间感三轴
Urgency
紧迫度
Tenacity
坚持度
Vigilance
警觉度
三条经验
  1. 状态栏用代码维护，不要让 LLM 批量统计历史。
  2. 删原始上下文前，先确认状态栏覆盖了所有可能被问到的问题。
  3. 把状态栏准确率当成一线生产指标。
09 / 上下文压缩策略

控制长度，防止 Context Rot

动机
  • 控制长度与成本
  • 提升思考质量
  • 防止上下文腐化
关键概念
  • Trace：agent_start → agent_end
  • Turn：一次模型调用 + 触发的工具执行
  • 保留区：切分点后原样保留的近期消息
四步流程
触发判断 → 找切分点 → 生成摘要 → 存储并重建上下文
对象是否压缩处理方式
System 提示词 ❌ 不压 保持原样，属于静态前缀
工具定义 ❌ 不压 保持原样，属于静态前缀
切分点之前的旧消息 ✅ 压缩 压成摘要
切分点之后的近期消息 ❌ 原样保留 默认约 20K token 的保留区
# 多次压缩：增量更新
1. 第二次压缩从上次保留区起点开始
2. 旧摘要作为 <previous-summary> 注入
3. 合并新对话后生成新摘要
核心原则
  • 不一次性倾倒全文
  • 超过阈值必须截断，但不能静默截断
  • 关键标识符必须原样保留
  • 隔离优于压缩：用子 Agent 让大体积中间信息不进入主上下文
