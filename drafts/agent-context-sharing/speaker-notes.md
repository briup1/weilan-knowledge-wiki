## Slide 2：一个让 Agent 突然变傻的故事

**时长**：3 min

**讲解**：
我们给客服 Agent 接了一个「查订单」工具。工具很老实，把订单的每一个字段都返回了，一个 JSON 就 4000 多个 token。下一轮 Agent 要判断「要不要退款」，结果它把用户那句「我想退款」给挤出上下文了，最后给了一个完全无关的建议。

问题不是工具错了，而是我们没意识到：上下文窗口是有限的，放进去的东西会互相竞争。

## Slide 4：上下文剖面图

**时长**：12 min

**讲解**：
一次 Agent 请求，上下文可以看成四层。最底层是静态前缀，包括 system prompt、claude.md、skill.md，这部分每次请求都带，最大也最稳定。往上是轨迹，也就是 user、assistant、tool、tool_result 的多轮历史，这部分最容易膨胀。再往上是动态提示词，某个 skill 被触发时才注入的详细说明。最上面是状态栏，当前会话的关键变量，比如用户身份、任务阶段、已确认字段。

一句话总结：上下文 = 固定前缀 + 历史轨迹 + 动态注入 + 当前状态。优化的本质，是在有限的 token 预算里放最相关的信息。

**Backup cut**：可将动态提示词与状态栏合并成一层讲解，节省 2–3 分钟。

**过渡到下一张**：剖面图里最值得先优化的是静态前缀，因为它一次性写好就能持续受益。

## Slide 5：静态前缀优化

**时长**：10 min

**讲解**：
System Prompt 可以当成新员工的入职手册，要回答四个问题：你是谁、不能做什么、输出什么格式、给一两个正面示例。少了任何一个，模型都容易跑偏。

Skill 和 Tool Prompt 要解决：什么时候调用、每个参数什么意思、有没有边界条件、能不能用更通用的描述替代多个定制工具。一个常见反模式是为「查订单」「查物流」「查库存」各写一个工具；更好做法是一个「查询后端 API」工具，通过 endpoint 参数区分场景。

**Backup cut**：可只保留 system prompt 四要素和反模式示例，省略参数细节。

**过渡到下一张**：静态前缀优化完后，下一个最快速膨胀的就是轨迹。

## Slide 6：轨迹与工具输出压缩

**时长**：12 min

**讲解**：
Agent 每走一步，user、assistant、tool、tool_result 都会被重新送进下一轮，token 数随步数线性甚至超线性增长。

压缩对象有三类：过时的 assistant 推理过程、oversized 的 tool_result，以及已经放在静态前缀里所以不必重复的说明。压缩时机分两种：单轮内，工具返回后立即压缩；跨轮，每 N 轮或 token 达到阈值时做一次总结。

对于工具返回的大量数据，三个策略：提取，只保留下一步需要的字段；指向，保留摘要，原始数据放到可检索的位置；分段，把大结果拆成多个小查询按需调用。最后简单区分一下 turn 和 trace：turn 是一次用户-Agent 交互回合，trace 是整个任务的结构化记录，用于观测，不一定要全塞进 prompt。

**Backup cut**：可跳过 turn/trace 概念，仅讲压缩对象与时机。

**过渡到下一张**：当上下文窗口真的装不下长期信息时，就需要记忆系统。

## Slide 7：记忆设计

**时长**：10 min

**讲解**：
记忆系统是「窗口外的长期上下文」。可以分成三层：工作记忆是当前会话的短期变量，比如用户刚确认的收货地址；Episodic 记忆是近期发生事情的摘要，比如过去 7 天的对话；语义记忆是长期稳定的知识，比如用户偏好、产品规则。

工作记忆通常直接放进状态栏；Episodic 和语义记忆通过检索按需注入动态提示词。核心原则是：不是所有记忆都要塞进 prompt，先检索，再决定放什么。

一句话总结：上下文管理解决「当下能装多少」，记忆设计解决「长期需要记得什么」。

**Backup cut**：可省略 Episodic/语义记忆的举例，只讲「先检索再注入」的原则。

**过渡到下一张**：最后我们把这些内容收束成一个可以带走的行动。
