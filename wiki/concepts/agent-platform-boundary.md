# Agent 平台边界

> 一个能力该收归平台、留给业务应用还是留在外部生态的判断方法。平台边界不是组织架构图，而是「哪些责任必须统一承担」的一组判据。

## 定义

当企业从一两个试点 Agent 走向多业务线并行时，模型调用、数据口径、工具副作用、审批与审计问题会跨 Agent 重复出现。**Agent 平台**是把这些共性问题收口到统一契约层、让每个业务 Agent 在同一底线上运行的组织与技术边界。它不同于 Agent 应用（解决单个业务任务）和 Agent 框架（编排单个 Agent 的状态、工具与记忆）：框架回答「如何把 Agent 写出来」，平台回答「如何让很多 Agent 在企业里长期存在并接受同一套约束」。

## 平台化的触发信号

三个信号同时出现时，平台化从可选项变成基础条件：

1. **重复建设**：不同团队重复封装模型、工具、RAG、审批、日志；
2. **治理断裂**：企业无法统一回答权限、成本、trace、评估问题；
3. **接入摩擦**：每个新 Agent 都要重新搭一遍基础设施。

经验规律：前两个试点可靠项目组经验撑住，从第三个起基础设施与治理成本集中爆发。

## 平台管理的五类共性问题

- **模型**：调用哪个模型、如何路由、限流、归集成本
- **数据**：能看哪些数据、什么口径、以什么身份访问、如何脱敏
- **工具**：有哪些能力、谁能调用、参数合法性、动作副作用
- **流程**：什么可自动执行、什么必须人工、长任务失败后如何恢复
- **治理**：如何评估、记录、回放、审计并持续改进

企业通常不是先有架构图再长出问题，而是重复问题先出现、平台随后被逼出来。Agent 平台区别于数据中台/应用中台：它以**模型决策为核心的任务执行链路**为自己的问题域。

## 边界判据

划分责任先问四个问题：

1. 这个能力会不会跨多个 Agent 重复使用？
2. 它是否影响权限、成本、审计或评估？
3. 它是否依赖某个业务域的特殊规则？
4. 平台化它是否会降低后续接入成本？

再加一个常被低估的维度——**变化速度**：变化慢且需稳定复用 → 越早平台化越好；变化快、试错频繁、依赖业务反馈 → 过早平台化会拖慢创新。

### 反向边界

平台过薄退化成模型网关，过厚吞掉业务逻辑。成熟平台只在必须统一处强约束、在允许差异处留插槽。平台不该做：替业务定义目标、吞掉所有业务规则、所有场景走同一流程、替代已有企业平台（应消费其能力）、消灭试错空间（应保留沙盒与准入分层）。

## 治理配套机制

- **准入流程**：任务定义 → 工具审查 → 风险分级 → 评测准备 → 平台接入（是否纳入统一 Runtime/Gateway/Trace/Policy）。
- **治理委员会**：稳定处理三类决策——准入决策（生产 vs 试点）、风险决策（必须审批/禁止自动执行的动作）、路线决策（哪些能力沉到平台）。不干预提示词、页面、业务文案。
- **平台目录**：每个 Agent 的运行档案（owner、风险等级、工具、模型、数据域、评测集版本、成本归属、退出条件），与准入/监控/成本视图联动，防止退化成静态清单。
- **退出机制**：低使用率、持续高成本、无人维护、风险升高无人接管 → 降级试点、改人工确认、冻结高风险工具或退役。
- **责任分工**：平台管统一入口/运行证据/工具契约/评测框架/发布门禁；业务管场景目标/验收样本/运营指标；数据管口径/权限/质量/血缘；安全法务管策略/审批/审计。
