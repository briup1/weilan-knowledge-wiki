# Agent Guardrails

Agent Guardrails 是平台上的控制系统：分类器识别风险，策略引擎决定动作，工具层限制权限，输出层做脱敏和结构校验，观测层管理误杀和漏杀。它不是一个内容审核 API，也不是单次工具调用前的格式检查。

## 分层

| 层 | 看什么 | 失败时 |
|---|---|---|
| 输入 | 用户消息、附件、URL、转写 | 拒绝、澄清、降级、转人工 |
| 上下文 | 检索片段、网页、工具返回、记忆 | 降权、脱敏、标出来源不可信 |
| 工具 | 谁在调用、参数范围、会不会写 | 拒绝或转 [[human-in-the-loop]] |
| 输出 | 回答、SQL、代码、导出 | 脱敏、结构校验、拦住外发 |
| 观测 | 误杀、漏杀、申诉 | 改策略，而不是只加拦截率 |

分类结果必须映射成拒绝、脱敏、审批、降级或放行。停在“高风险”三个字上，运行时无法执行。通用类别之外，企业还要有自己的金融、医疗、隐私和品牌类别。

## 和相邻控制的差别

- [[validation-loop]] 挡的是参数格式、危险命令和重复失败。Guardrails 决定一段内容和一次动作能不能过企业政策。
- [[hybrid-agent-evaluator]] 在任务跑完后判断质量。Guardrails 在运行当时做允许或拒绝。
- [[agent-security]] 里的框架级命令黑名单仍然有用。企业平台还要把间接注入和工具越权放进同一条策略，因为攻击经常藏在检索内容和工具结果里，不在用户那一句输入里。

## 运营

脱敏要发生在进模型前、检索组装时、工具返回后、展示前、写日志和导出时。答案里没有手机号，不代表 Trace 或浏览器状态里没有。

不要只看拦截率。同时看误杀率、漏杀数和审批通过率。策略要有负责人、版本、灰度和申诉。早期目标是每次决定都能追踪、每次误杀漏杀都能变成回归样例，不是一次拦住所有风险。
