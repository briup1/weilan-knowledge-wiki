# Human-in-the-loop

Human-in-the-loop 是在高风险动作执行前，把授权交给有权限的人，并让任务在同一条 Run 上暂停和恢复。它是治理能力，不是模型答不好时临时加的聊天追问。

## 和澄清分开

澄清发生在规划前，用来补全任务输入。审批发生在 Runtime 准备执行高风险动作或发布产物之前，用来授权。把审批做成对话里的一句“可以吗”，后面却新开一次请求，审计就对不上人批的是哪一版。

## 三种审批

| 模式 | 什么时候停 | 适合什么 |
|---|---|---|
| 前置审批 | 工具执行前 | 转账、删除、改主数据 |
| 后置审批 | 草稿已经生成，发布或外发前 | 报告、邮件、公告 |
| 分级审批 | 多个角色依次或会签 | 金额、法务、对外承诺 |

批准后，[[agent-run-lifecycle]] 在同一个 `run_id` 上从检查点继续。拒绝进入失败，并记下结构化原因。不要在原 Run 里悄悄改掉已批准的产物再往下跑。

取消是放弃未完成的动作，已经发生的副作用要补偿或人工处理。暂存是继续停在 `waiting_human`，等材料，不是新任务。

## 两类检查点

引擎检查点给 Runtime 恢复，保存执行状态、工具结果和记忆引用。业务检查点给控制台和合规回放，保存草稿、审批里程碑和展示状态。两者对齐到同一个 `run_id`，读取方和字段不同，不能合成一份什么都往里塞的快照。

业务回放至少要回答四件事：谁批准的、依据哪份数据、发布的是哪个版本、模型有没有越过人工。技术 Trace 证明系统做了什么，见 [[agent-trace]]。它代替不了这张责任回放。

## 边界

长任务不要占着一条同步连接。用异步队列、检查点和事件日志。审批超时要单独算，不能和模型超时混成一个数。前端按钮只是这条状态的投影；按钮能点、后端却另起一趟执行，就算失败。
