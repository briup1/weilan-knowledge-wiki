# 第2章 企业级 Agent 平台的边界

## 摘要

本文是《企业级 Agent 平台工程》第 2 章。它把「平台边界」从组织架构图/采购清单中剥离，定义为**「哪些责任必须统一承担」的判断方法**：当企业从一两个单点 Agent 走向十几个 Agent 并行时，模型、数据、工具、流程、治理五类共性问题必须收口到统一平台层，否则只是「一组互不相认的试点」。章节给出触发平台化的三个信号、边界划分的四问判据、准入与治理委员会机制、平台目录与退出机制，以及「平台不该做什么」的反向边界，强调平台过薄会退化成模型代理、过厚会吞掉业务规则。

## 核心要点

- **三层边界**：Agent 应用解决具体业务任务（报价/工单/DataAgent）、Agent 框架编排单个 Agent（LangGraph/AutoGen/CrewAI）、Agent 平台让多 Agent 共享能力并统一治理。低代码/Agent Studio 解决了「快速搭应用」≠ 解决了平台问题。
- **平台化触发三信号**：重复建设（各团队重复封装模型/工具/RAG/审批/日志）、治理断裂（无法统一回答权限/成本/trace/评估）、接入摩擦（每个新 Agent 重新搭基础设施）。三信号齐现时平台化从可选项变成基础条件。
- **五类共性问题**：模型（路由/限流/成本归集）、数据（口径/访问身份/脱敏）、工具（注册/权限/参数合法性/副作用）、流程（自动 vs 人工/长任务恢复）、治理（评估/记录/回放/审计）。
- **边界划分四问**：是否跨多 Agent 复用？是否影响权限/成本/审计/评估？是否依赖业务域特殊规则？平台化是否降低后续接入成本？另加**变化速度**维度：变化慢且需稳定复用的能力越早平台化越好，变化快试错频繁的业务逻辑过早平台化会拖慢创新。
- **归属示例**：模型调用入口、工具注册与风险等级、统一审批通道、统一 trace 字段与 run_id 规范 → 平台；报价折扣规则、工单优先级策略 → 应用；语义层底座 → 平台为主，业务解释细节平台与应用共担。
- **平台不该做**（反向边界表）：替业务定义目标（责任错位）、吞掉所有业务规则（发布被业务变化拖垮）、所有场景同一流程（应风险分级）、替代已有数据/身份/审批平台（应连接增强）、消灭试错空间（应留沙盒与准入分层）。
- **治理机制**：新 Agent 准入五步（任务定义→工具审查→风险分级→评测准备→平台接入）；治理委员会稳定处理三类决策——准入决策（能否进生产）、风险决策（哪些动作禁自动执行）、路线决策（哪些能力沉到平台）。委员会不干预提示词/页面/业务文案。
- **责任四方分工**：平台负责统一入口/运行证据/工具契约/评测框架/发布门禁；业务负责场景目标/验收样本/运营指标/用户反馈；数据负责口径/权限/质量/血缘；安全法务内控负责策略/审批/审计要求。
- **运营与目录**：平台是长期运营系统而非一次性交付，运营含场景/质量/成本/风险/生态五类工作；平台目录记录 owner、风险等级、工具、模型、数据域、评测集版本、成本归属与退出条件，需与准入/监控/成本视图联动，不能退化成静态清单。
- **退出机制**：低使用率、持续高成本、无人维护、风险升高无人接管 → 降级试点/改人工确认/冻结高风险工具/退役。供应商产品接入须支持统一身份权限、数据工具边界、trace 导出、评估、成本视图与治理策略掌控，避免变成治理孤岛。
- **早期采用节奏**：先收生产风险最高、跨场景复用最多的能力（模型网关、工具登记、运行状态、Trace、基础评测、策略拦截、发布记录）；与风险分级绑定（低风险标准接入、中风险补审查确认、高风险要求 Policy/HITL/Trace/回滚）；分步迁移，每步迁移都要带来可见收益。
