## Post

Here is the graph that fixed it: I split one loop into 3 nodes. Approval went from 45% to 82.5%. Cost went up 60%. This is the exact week it happened, the code, and the function I now run before building a single node.

TLDR: if you don't want to read the whole thing, the decision function and the three-node graph are both at the bottom. Copy the function first, build nothing until it tells you to.

# Introduction
A loop is one agent running discover, plan, execute, verify on repeat until a condition is met. It is genuinely enough for most agent work. Fix the failing tests, draft and self-review a page, triage an inbox, research one question and write it up. All of those are loops. None of them need more than that.

The mistake is not staying in the loop too long. The mistake is not noticing the one moment a loop actually breaks, and reaching for a graph either way too early, out of hype, or way too late, out of habit.

I stayed in a loop for six months across a dozen small pipelines. Then one pipeline broke in a specific, nameable way, and I want to show you that exact break instead of the abstract argument for graphs you have probably already read this month.

# Why My Loop Stopped Compounding
Before the break, here is what six months of loop-only building actually looked like, warts included:

- A pipeline that nailed the first ten outputs and quietly degraded on the eleventh, because nothing was watching for that
- A self-review step that agreed with its own writer more often than a stranger would have
- A task I kept re-running by hand because I did not trust the loop's own verdict
- A "good enough" bar I never wrote down, so I graded the same kind of output differently on different days
- Output I read once, approved, and never looked at again, which meant I was the only quality control that existed

None of that is a graph problem specifically. It is what happens when one agent is doing more than one job and nothing outside that agent is allowed to say no to it.

# The One Thing That Actually Forces A Graph
Cut through every framework and every diagram and there is one sentence underneath all of it.

&gt; If the thing that produced the output is also the thing that grades it, you do not have quality control, you have a rubber stamp with extra steps.

That is true inside a single loop too, and it is why a stronger prompt does not fix it. A loop has nowhere to put the fix, because there is only one context and it already picked a side. A graph has somewhere to put it: a separate node, with its own instructions, whose only job is to say no.

Everything below is what happened when I gave that job a place to live.

# The Pipeline That Broke
The task: research a topic, write a draft, and catch the draft's own mistakes before it ships. I ran it as one loop for a week, because that is the default and the default is usually right.

It worked, technically. It also produced drafts that read like someone half paying attention to three jobs at once. Out of 40 drafts across two weeks, 31 passed self-review on the first try. When I read them manually myself, only 18 were actually publish-ready.

That gap, 31 versus 18, is the whole argument in one number. Thirteen drafts shipped a passing grade from a reviewer that had every incentive to pass its own writing.

# Station 1: The Node Contract
Before I wrote a single node, I wrote down what each one was allowed to touch. This is the part everyone skips, then rebuilds by accident three bugs later.

A contract like this written for a folder full of prompts is decoration. It only becomes real once something enforces it in code, not in the instructions you hope the model reads carefully.

# Station 2: What Actually Changed
I broke the single loop into three nodes and one conditional edge.

- **Researcher**: pulls sources, writes structured notes, nothing else.
- **Writer**: only sees the notes and the task, never sees its own prior drafts unless the reviewer sends one back.
- **Reviewer**: a separate model call with a narrower instruction set, whose only job is to check the draft against the contract's bar, not to write anything.

Same 40-draft workload, same two weeks, now split across the graph. First-pass approval rate on manual read went from 18 out of 40 to 33 out of 40. The reviewer node rejected 14 drafts and sent them back, and every one of those rejections had a specific, quotable reason attached, because the reviewer was not also the author defending its own choices.

# Station 3: Shared State Is The Part Nobody Designs On Purpose
The single biggest mistake I made early on was letting each node write whatever it wanted into state. A researcher would casually overwrite a field the writer depended on, and I would spend an hour debugging a draft that referenced sources that no longer existed in the notes.

The fix was a strict object and one owner per field, enforced, not assumed.

State drift is the number one way a graph rots over time. If you cannot say who owns each field, you do not have a graph yet, you have a shared mutable mess.

# Station 4: The Router Is Where The Real Decision Lives
The conditional edge from reviewer back to writer is not magic, it is a plain function that reads the verdict and picks the next node.

That escalate branch mattered more than I expected. Two of the 14 rejected drafts never passed after a second rewrite either, and the router sent them to me instead of looping a third time and burning tokens on a task the writer genuinely could not fix alone.

# Station 5: The Cost Nobody Puts In The Tweet
The graph is not free. Three nodes meant three model calls per draft instead of one, and the reviewer's rejection loop added a second writer pass on 14 out of 40 pieces.

That tradeoff was worth it for me because a bad draft costs more in edit time than three model calls ever will. It will not be worth it for a task with a clear, cheap, mechanical finish line. If your loop is "fix the failing test" or "summarize this thread," do not build a graph, you will just be paying triple for the same answer.

# The Guards, All Reproducible
Every one of these is a way the pipeline would have quietly shipped garbage if it were not caught in code.

Five failure modes, five refusals. Each one is a bug I would have shipped without noticing if the check lived in a prompt instead of in code.

# Station 6: The Function I Run Before Adding A Single Node
I stopped deciding this by feel and turned my own checklist into code I run against a task description before touching an orchestration framework.

Run your task through that before you open a diagramming tool. Most tasks return "loop." Mine did too, for six months, until the research and write and review pipeline finally did not.

# Your First Week, If You're Doing This For The First Time
- **Day 1**: Pick the loop that is quietly underperforming, not the one that is obviously broken. Obvious breaks get fixed. Quiet ones get shipped for months.
- **Day 2**: Read 20 of its outputs by hand, not the ones the loop's own verdict flagged. Count how many you would actually approve. That number is your real baseline, not the one the loop reports about itself.
- **Day 3**: Write the node contract before the node. Reads, writes, cannot-write, bar. If you cannot fill in "cannot_write," you have not thought about it enough yet.
- **Day 4**: Split the verifier first, before adding any specialist node. It is the cheapest, highest-leverage change in this entire guide.
- **Day 5**: Add the ownership map and the guarded writes. Try to make one node write another node's field on purpose, and confirm it fails loudly.
- **Day 6**: Write the router as a plain function with an escalation cap. Run the same 20 outputs from Day 2 back through it and compare.
- **Day 7**: Price it. Count model calls per output, before and after. Decide, in writing, whether the jump in approval rate was worth the jump in cost. Do not skip writing it down, the honest number is easy to forget once the pipeline is running well.

# What I Haven't Built
Being straight about the edges of this, because a guide that only lists wins is not a guide.

- The router only handles three nodes right now. I have not tested it past that, and I expect the ownership map gets harder to keep honest around five or six.
- The escalation path dumps the task on me with no triage. It should rank escalations by how close they got, and it does not yet.
- Revision count resets per run, not per task type. A task that reliably needs two rewrites should probably start the writer with a stricter bar instead of discovering that on attempt two, every time.
- The 60 percent cost number is from one pipeline, not a general constant. Treat it as "expect a real number here," not as a rule.

# The Playbook
- 3 nodes: researcher, writer, reviewer, one job each, one contract each
- 1 router function deciding ship, retry, or escalate
- 1 state object, one owner per field, guarded writes, no shared writes
- 1 law: the node that produced the output is never the node that grades it
- 5 guards, all reproducible, all caught in code instead of in a prompt
- 40 drafts tested, 18 passing on manual read before the split, 33 after
- 14 drafts rejected and sent back, 2 escalated to a human instead of looping forever
- +60% inference cost per finished draft, paid for a jump from 45% to 82.5% approval
- 7 days from first contract to a priced, working graph

# In Short
I showed you the exact week a loop of mine stopped being enough, and the graph that replaced it.

**What it does for you.** It stops one overloaded agent from grading its own homework, by giving the grading job its own node, its own context, and a contract it cannot write outside of.

**Why that was hard before.** Inside a single loop there is nowhere to put the fix. The same context that writes the draft is the only thing available to check it, so a stronger prompt just asks the same biased judge to try harder.

**What solves it.** Not five nodes. One split verifier, one router function, one ownership map. Everything past that is optional complexity you add only when a specific job in your task is asking for it by name, not because the diagram looks more serious with it.
