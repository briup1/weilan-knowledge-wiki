## 为什么值得阅读

这篇文章用生产工程视角区分“模型评测”和“Agent 系统评测”，给出任务成功、完整轨迹、工具使用、推理效率和业务自定义指标五个落地方向。它适合作为企业评测平台指标体系和 Trace 采集规范的简明基线。

## 主要内容中文译介

传统模型 Benchmark 多在静态题目上评估知识、推理、编码或指令遵循；Agent Eval 则面对动态环境中的端到端行为，需要观察 Agent 是否正确规划、调用工具、处理异常并真正完成工作。即使底层模型能力很强，Agent 也可能因为参数 Schema 幻觉、错误重试或循环失控而失败。

文章提出五项实践：

1. **优先衡量任务成功率**：Task 应由业务意图和约束共同定义，例如必须使用指定 API、限制工具调用次数或满足副作用条件；应分别统计正常、工具降级、指令含糊等场景。
2. **评估完整轨迹**：记录计划、子目标、工具调用与响应、中间依据、最终答案及写入/更新等副作用。两个 Agent 即便得到同一答案，其成本、风险和执行质量也可能完全不同。
3. **把工具使用作为一等信号**：为任务声明允许或必须使用的工具、最大调用次数和参数 Schema，测量工具选择精确率/召回率、Schema 合规率和重试情况。
4. **同时评价推理质量和效率**：检查是否利用检索证据，统计每次成功任务的 Token、步骤、工具次数和端到端时延，并以预算约束优化提示词、路由和重试策略。
5. **从原型期建设透明、可定制的评测**：为计划和工具步骤分配稳定 ID，给轨迹附加成功、失败类型和人工评分标签，同时支持通用指标与行业专用指标。

## 方法与评估设计

- **评测对象**：包含模型、提示词、工具、编排和外部环境的完整 Agent 系统。
- **核心指标**：Task Success Rate、Trajectory Efficiency、Tool Call Accuracy、工具选择精确率/召回率、Schema 合规率、Token、步骤数、时延和业务自定义 KPI。
- **数据切片**：正常流程、异常/降级工具、歧义输入和行业特定风险场景。
- **可观测性**：以稳定标识串联计划、工具、观察、结果和副作用，支持逐条失败分析。
- **工程闭环**：评测从开发第一天进入日常迭代，而不是上线前临时补建。

## 对企业级平台的启示

1. Trace Schema 要覆盖工具请求/响应、错误、重试、状态写入和业务副作用，不能只采集 LLM span。
2. 指标应按场景、工具、Agent 版本和失败类型切片，聚合总分不能替代诊断视图。
3. 平台需要预算型评估器，例如“95% 成功任务不超过 N Token、M 次工具调用和 T 秒”。
4. 工具注册信息应与评测资产关联，自动校验 Schema、权限、调用次数和必需工具。
5. 通用指标与业务 Rubric 应分层管理，避免每个团队重复建设同名但口径不同的指标。
