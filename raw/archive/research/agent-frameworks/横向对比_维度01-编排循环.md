# 横向对比：维度01 — 编排循环（Orchestration Loop）

> 四个框架：Hermes Agent（Python）、nanobot（Python）、OpenClaw（TypeScript）、OpenCode（TypeScript）

---

## 1. 一句话概括差异

| 框架 | 编排循环的"灵魂" |
|------|-----------------|
| **Hermes Agent** | 带预算控制的**可中断 ReAct 循环**，以线程级中断信号和并发工具执行为特色 |
| **nanobot** | **两层嵌套的 actor + ReAct 循环**，以纯函数式消息处理和全局锁串行化为特色 |
| **OpenClaw** | **五层分层状态机 + 管道**，以双层队列、模型降级链、compaction 快照回退为特色 |
| **OpenCode** | **单线程流式事件驱动循环**，以 inline 子任务执行和 doom loop 检测为特色 |

**核心分歧**：编排循环到底是"一个 while(true)"还是"多层嵌套的恢复策略调度器"？Hermes 和 nanobot 倾向前者——循环本身简单，复杂度在循环内部的工具执行和中断处理上；OpenClaw 倾向后者——循环是分层的，每一层负责一种故障恢复维度；OpenCode 则走了极简路线——单线程、流式、让 AI SDK 处理大部分流控制。

---

## 2. 循环结构对比

### 2.1 层级深度

```
Hermes Agent:   CLI process_loop → chat(agent_thread) → run_conversation(while) → _execute_tool_calls
                                                                                      └── concurrent(ThreadPool)
nanobot:        run(message_pump) → _dispatch(asyncio.Lock) → _process_message → _run_agent_loop(while)
OpenClaw:       Gateway(while) → Lane(drainLane) → Run(while retry) → Attempt(single) → Stream(draft_loop)
OpenCode:       SessionPrompt.loop(while) → SessionProcessor.process(stream) → tool execution
```

**关键洞察**：

- **Hermes 和 nanobot** 的循环层级是 2-3 层，且外层负责调度/中断，内层负责 ReAct 推理。两者都把"什么时候停"的决策内嵌在 while 条件里。
- **OpenClaw** 的循环层级是 5 层，每一层都有独立的退出/恢复语义。Gateway 管 SIGUSR1，Lane 管并发，Run 管模型降级，Attempt 管 compaction，Stream 管节流。这种分层让每一层可以被独立测试和替换，但增加了理解成本。
- **OpenCode** 只有 2 层，但把子任务执行 compaction 都塞进了同一层循环的 if/continue 分支中，导致循环内部逻辑复杂但层次扁平。

**启示**：循环层级数与框架的目标场景强相关。个人助手（nanobot）和 CLI 工具（Hermes）可以用 2-3 层；网关服务（OpenClaw）必须用 5 层来隔离故障域；IDE 插件（OpenCode）用 2 层但通过流式事件模型降低复杂度。

### 2.2 循环退出条件

| 框架 | 主退出条件 | 兜底退出 | 退出后动作 |
|------|-----------|---------|-----------|
| **Hermes** | LLM 不返回 tool_calls | `max_iterations` + `IterationBudget` 耗尽 → grace call | `_persist_session()` + `_cleanup_task_resources()` |
| **nanobot** | `response.has_tool_calls == False` | `iteration >= 40` → "达到最大轮次" 文本 | `_save_turn()` + `sessions.save()` + 后台记忆压缩 |
| **OpenClaw** | attempt 成功返回 payload | 多级恢复链耗尽 → 用户友好错误文本 | 构建 ReplyPayload 交付 |
| **OpenCode** | `lastAssistant.finish` 不是 `"tool-calls"` 也不是 `"unknown"` | 无显式迭代上限（依赖 agent.steps 配置） | session 状态由 DB 持久化 |

**关键洞察**：

1. **预算控制的哲学差异**：Hermes 最精细（双保险：迭代次数 + IterationBudget + grace call），nanobot 最朴素（硬编码 40 轮），OpenClaw 把预算概念分散到各层（MAX_RUN_LOOP_ITERATIONS 动态计算、COMPACTION_RETRY_AGGREGATE_TIMEOUT_MS = 60s），OpenCode 最信任模型（无硬编码上限，依赖 agent 配置）。

2. **"预算耗尽后怎么办"是用户体验的分水岭**：Hermes 的 grace call 给模型一次"总结发言"的机会，用户看到的是自然收尾而非硬截断。nanobot 给用户提示"建议拆小步骤"。OpenClaw 返回"Request failed after repeated internal retries"。OpenCode 没有这个场景（信任 agent.steps）。**Hermes 的做法最值得借鉴**——预算是必要的，但预算耗尽的体验比预算本身更重要。

3. **循环终止信任谁**：nanobot 完全信任 `has_tool_calls` 协议字段，OpenCode 完全信任 `finish` 原因，Hermes 和 OpenClaw 更不信任模型——前者加了 grace call，后者加了整个恢复链。**对模型的信任程度与框架的部署场景正相关**：个人助手可以信任模型，网关服务不能。

## 3. 并发模型对比

这是四个框架差异最大的维度。

### 3.1 并发策略矩阵

| | **Hermes** | **nanobot** | **OpenClaw** | **OpenCode** |
|---|-----------|------------|-------------|-------------|
| 基础并发模型 | `threading` + `ThreadPoolExecutor` | `asyncio` + `asyncio.Lock` | 事件循环 + 双层队列 | 单线程事件循环 |
| 工具执行并发 | ✅ ThreadPoolExecutor(max=8)，静态白名单 | ❌ 串行，逐个执行 | ❌ 串行（由 Lane 保证） | ❌ 串行 |
| 会话级并发 | 每会话独立线程 | 全局锁串行所有会话 | Session Lane 串行，Lane 间并行 | 单会话单线程 |
| 中断模型 | per-thread `set[int]` + 级联传播 | `asyncio.Task.cancel()` | Lane generation + abort signal | AbortController |
| 对 Python GIL 的态度 | 主动规避（IO-bound 工具在线程中受益） | 天然规避（asyncio 是协作式并发） | N/A（TypeScript） | N/A（TypeScript） |

**关键洞察**：

1. **工具级并发是 Hermes 的独特优势**：Hermes 是唯一一个支持多工具并行执行的框架。`_should_parallelize_tool_batch()` 用静态白名单 + 路径重叠检测做决策——保守但零误伤。其他三个框架都是串行执行工具。在"需要同时读多个文件"或"同时搜索多个关键词"的场景下，Hermes 的吞吐优势明显。

2. **nanobot 的全局锁是刻意的权衡**：`_processing_lock` 是单实例 `asyncio.Lock()`，所有会话共享。这在"个人助手 + 单 LLM 后端"场景下完全合理——并发推理只会抢 token 配额和 rate limit。但如果要做多用户服务化，这是第一个需要改的地方。

3. **OpenClaw 的双层队列是最精细的并发控制**：外层 session lane 保证同会话串行（防 session file 写锁竞争），内层 global lane 控制全局并发数（防资源爆炸）。加上 `generation` 机制处理 SIGUSR1 后的遗留任务，是生产级网关的标配。

4. **并发模型的选型与语言强绑定**：两个 Python 项目分别选了 threading（Hermes）和 asyncio（nanobot），体现了 Python 生态中两种并发范式的对立。两个 TypeScript 项目都基于事件循环，但 OpenClaw 在事件循环上构建了更复杂的队列层。

### 3.2 中断机制对比

| | **Hermes** | **nanobot** | **OpenClaw** | **OpenCode** |
|---|-----------|------------|-------------|-------------|
| 中断粒度 | 线程级（per-thread ID） | 任务级（asyncio.Task.cancel） | Lane 级（generation 标记） | 会话级（AbortController） |
| 中断传播 | 三层：主线程 → 工作线程 → 子 Agent | 单层：cancel task | 双层：abort run → drain lane | 单层：abort |
| API 调用中断 | ✅ 后台线程 + 0.3s 轮询 + 关闭专用 client | ❌ 依赖 asyncio cancel 语义 | ✅ abort signal + timeout | ✅ input.abort.throwIfAborted() |
| 中断能否打断 LLM 推理 | ✅ 可以（关闭底层 HTTP 连接） | ⚠️ 取决于底层 HTTP 库 | ✅ 可以（abort + timeout） | ✅ 可以（abort） |
| 中断后资源清理 | `_cleanup_task_resources(task_id)` | `close_mcp()` drain 后台任务 | `completeTask` generation 检查 | DB 状态自然持久化 |

**关键洞察**：

1. **Hermes 的线程级中断是网关场景的刚需**：全局 `threading.Event` 在多会话网关下是灾难——一个会话的中断会杀死所有会话。Hermes 用 `set[int]` 精确到线程 ID，并做三层级联传播。这是"网关级 Agent"必须解决的架构问题，nanobot 和 OpenCode 作为单会话工具不需要考虑这个。

2. **API 调用的可中断性是被低估的设计**：LLM 推理可能持续 30 秒以上，如果不可中断，用户按 Ctrl+C 后要等模型跑完。Hermes 用"后台线程 + 主线程轮询"模式，OpenClaw 用 abort signal，OpenCode 用 AbortController。nanobot 依赖 asyncio cancel 语义——在大多数情况下能工作，但不如显式的 HTTP 连接关闭可靠。

3. **中断后的资源清理是最容易忽略的**：Hermes 和 OpenClaw 都有显式的清理路径。nanobot 的 `close_mcp()` drain 后台任务是一个容易被遗漏的细节——如果进程退出时不等后台任务完成，记忆归档可能丢失。

## 4. 错误恢复策略对比

这是 OpenClaw 与其他三个框架拉开最大差距的地方。

### 4.1 恢复策略层级

| | **Hermes** | **nanobot** | **OpenClaw** | **OpenCode** |
|---|-----------|------------|-------------|-------------|
| Context Overflow | 无专门处理 | 入口前同步压缩一次 | 恢复链：compaction → 工具结果截断 → 失败 | 循环内检测 → 创建 compaction 任务 → continue |
| API 错误 | 指数退避重试 + provider fallback | `chat_with_retry` 封装 | Profile 轮换 → thinking 降级 → model fallback | 无专门处理（依赖 AI SDK） |
| Rate Limit | 无专门处理 | 无专门处理 | Auth Profile cooldown 探测 + 跳过 | 无专门处理 |
| 认证失败 | 无专门处理 | 无专门处理 | Copilot token 刷新 → Profile 轮换 → 失败 | 无专门处理 |
| 错误响应 | 写入历史 | ⚠️ **不写入历史**（#1303 事故修复） | 取决于错误类型 | 无专门处理 |
| Compaction 一致性 | 无专门处理 | 无专门处理 | ✅ preCompactionSnapshot 快照回退 | 无专门处理 |

**关键洞察**：

1. **OpenClaw 的恢复策略是"防御式编排"的教科书**：它把 LLM 的混沌输出（超时、rate limit、context overflow、auth failure）转化为确定性的系统行为。恢复策略按成本排序：compaction（纯计算）< 工具结果截断（局部修改）< Profile 轮换（切换 key）< thinking 降级（降低能力）< model fallback（切换模型）。这种"低成本优先"的排序是最小化用户感知延迟的关键。

2. **nanobot 的"错误不入历史"是反直觉但极重要的工程经验**：`finish_reason=="error"` 时直接 break 不持久化，背后是 issue #1303 的真实事故——错误响应写入历史后，下一轮 LLM 看到畸形 assistant 消息，反复触发 400，形成"毒消息→永久 400"死循环。**只有 4 行代码，但能挡住整类"会话毒化"事故**。其他三个框架都没有这个防御。

3. **OpenCode 把 compaction 当作循环内的一种"系统级任务"**：检测到上下文溢出 → 创建 compaction 任务 → continue 重新进入循环。这比 OpenClaw 的五层恢复链简单得多，但在 IDE 场景下足够用——用户不会因为 compaction 失败而丢失工作。

4. **Hermes 的 API 错误重试是最务实的**：`_interruptible_api_call` + 指数退避 + provider fallback，没有 OpenClaw 的复杂层级，但覆盖了最常见的失败模式。对于 CLI 工具来说，这比五层恢复链更实用。

## 5. 子任务/子 Agent 执行模式对比

| | **Hermes** | **nanobot** | **OpenClaw** | **OpenCode** |
|---|-----------|------------|-------------|-------------|
| 执行模式 | 异步派发，独立预算 | SpawnTool 通过 bus 回灌 | Steer / Queue 双模式 | Inline 同步执行 |
| 预算隔离 | 父子独立预算 | 共享主循环预算 | 独立 run | 无独立预算 |
| 中断传播 | 三层级联（子 Agent 递归 interrupt） | cancel task | abort signal | 共享 AbortController |
| 结果交付 | 直接返回 messages | `bus.publish_inbound` 回灌主会话 | Steer（运行中注入）/ Queue（空闲时等待） | 直接写入 session DB |
| 嵌套支持 | ✅ 递归子 Agent | ✅ 子 Agent 可再 spawn | ✅ wake-on-descendant | ✅ TaskTool 可嵌套 |

**关键洞察**：

1. **OpenCode 的 inline 执行是最简洁但最危险的**：`TaskTool.execute` 同步阻塞主循环执行子任务，整个 session 在子任务执行期间无响应。优点是实现简单、因果顺序清晰；缺点是长子任务会完全冻结 UI。其他三个框架都把子任务异步化。

2. **OpenClaw 的 steer/queue 双模式最精细**：父会话正在运行时用 steer 直接注入消息，空闲时用 queue 等待下次运行。`wake-on-descendant` 解决了嵌套子代理的"最后一公里"问题。这是唯一一个区分"父忙"和"父闲"两种状态的框架。

3. **Hermes 的级联中断是最完善的**：`interrupt()` 递归调用所有 `_active_children` 的 `interrupt()`，确保任意深度的任务树都能被干净中断。这是"网关级 Agent"必须具备的能力。

4. **nanobot 的 bus 回灌是最解耦的**：子 Agent 通过 `bus.publish_inbound` 把结果作为新的 InboundMessage 推回主会话，主循环无需知道子 Agent 的存在。这种"子 Agent 只是另一个消息源"的设计，让子 Agent 的生命周期管理完全独立于主循环。

## 6. 用户交互与可观测性对比

| | **Hermes** | **nanobot** | **OpenClaw** | **OpenCode** |
|---|-----------|------------|-------------|-------------|
| 中途干预 | `/steer` 注入最后工具结果 | `/stop` cancel task | Steer message 注入 | AbortController 取消 |
| 进度反馈 | 无专门机制 | ✅ 思考摘要 + 工具调用提示 | ✅ Draft stream 节流输出 | ✅ 流式事件（text-delta） |
| 流式输出 | 无专门处理 | 无专门处理 | ✅ draft-stream-loop（节流 + in-flight 管理） | ✅ AI SDK fullStream |
| 心跳/Cron | 无 | ✅ `/new` + 后台归档 | ✅ 完整 Cron 调度器 + 心跳 | 无 |

**关键洞察**：

1. **nanobot 的 steer 机制设计最精巧**：不中断循环，将用户备注注入最后一个 tool result 的 content 中，附以 `"User guidance:"` 标记。这样既让模型在下一轮看到用户意图，又不破坏 `user/assistant/tool` 的 role alternation 约束。相比之下，Hermes 的 `/steer` 是同样的思路，而 OpenClaw 和 OpenCode 没有类似机制。

2. **OpenClaw 的 draft stream loop 是唯一处理"流式节流"的**：LLM 的 token 到达频率可能远高于消息平台的发送频率限制。`createDraftStreamLoop` 通过 `inFlightPromise` + `throttleMs` + `pendingText` 三者配合，保证消息顺序且不触发 rate limit。其他框架要么不做流式输出，要么直接转发不过滤。

3. **进度回调是用户体验的隐形分水岭**：nanobot 的 `_tool_hint`（显示 `read_file("src/main.py")` 这样的摘要）和思考摘要让用户在 30 秒沉默中保持信心。OpenCode 的流式 text-delta 让 IDE 实时显示模型输出。Hermes 和 OpenClaw 虽然功能更强大，但在"用户等待时的心理安慰"上投入不足。

## 7. 消息处理与防御性编程对比

| | **Hermes** | **nanobot** | **OpenClaw** | **OpenCode** |
|---|-----------|------------|-------------|-------------|
| 消息清理 | ✅ `_sanitize_api_messages`：孤儿修复 + stub 注入 | ✅ `_save_turn`：截断 + 剥 runtime context | ✅ session sanitize history | 无专门处理 |
| API 请求与持久化分离 | ✅ `messages`（持久化）vs `api_messages`（请求副本） | ✅ `_run_agent_loop` 纯函数返回新列表 | ✅ snapshot 机制 | ✅ DB 持久化与 stream 分离 |
| 错误响应隔离 | 写入历史 | ⚠️ 不写入历史 | 取决于错误类型 | 无专门处理 |
| Provider 兼容性 | `_drop_thinking_only_and_merge_users` | `_strip_think` 剥 `heden` 块 | Provider-specific stream 解析 | Synthetic user message for Gemini |

**关键洞察**：

1. **"API 请求副本 vs 持久化历史"的分离是通用模式**：Hermes、nanobot、OpenClaw 都做了这个分离，只是实现方式不同。Hermes 在每次 API 调用前复制 `api_messages` 并 sanitize；nanobot 的 `_run_agent_loop` 是纯函数返回新列表；OpenClaw 用 snapshot 快照。这说明在 LLM Agent 中，"给模型看的消息"和"存下来的消息"必须是两个东西——前者需要适配 provider 的 schema 要求，后者需要保持完整性和可审计性。

2. **nanobot 的 `_save_turn` 是最全面的"消毒"**：截断超大 tool result（16K 字符）、剥离 runtime context 前缀（保持 prompt cache 友好）、过滤空 assistant 消息、替换图片 base64 为占位符。这种"写入前消毒"的思路值得所有框架借鉴——写入 session 的内容会成为下次推理的上下文，不消毒的话问题会随时间累积。

3. **Provider 兼容性是隐性成本**：Hermes 处理 "thinking-only" assistant 消息（Anthropic），nanobot 剥 `heden` 块（DeepSeek-R1），OpenCode 为 Gemini 插入 synthetic user message。每个框架都要为自己的 target providers 做特殊适配，这部分代码看似简单但极容易出 bug。

## 8. 设计哲学总结

### 8.1 四种哲学

| 哲学 | 代表框架 | 核心信念 | 适用场景 |
|------|---------|---------|---------|
| **务实主义** | Hermes Agent | 循环要简单，中断要可靠，工具可以并发 | CLI / 网关，需要同时服务多个用户 |
| **极简主义** | nanobot | 循环分两层就够了，内层要纯函数，错误不入历史 | 个人助手，单用户单后端 |
| **防御主义** | OpenClaw | LLM 是不可靠的，每一层都要有独立的恢复策略 | 生产级网关，7×24 运行 |
| **信任主义** | OpenCode | 让 AI SDK 处理流控制，循环只管调度 | IDE 插件，用户在旁边看着 |

### 8.2 最重要的共性发现

尽管四个框架差异巨大，以下模式是共通的：

1. **ReAct 是默认范式**：所有框架都是"LLM 推理 → 工具执行 → 结果回灌 → 再推理"的循环，没有任何框架采用 Plan-and-Execute 或其他范式。这说明在当前模型能力下，ReAct 仍然是最实用的 Agent 编排模式。

2. **循环终止条件都依赖模型的 tool_calls 协议**：无论框架复杂度如何，"模型不再请求工具"都是循环的主要退出条件。这意味着所有框架都把自己的命运部分交给了 LLM provider 的协议实现质量。

3. **消息持久化与 API 请求必须分离**：四个框架都用不同方式实现了这个分离。这不是巧合，而是 LLM API 的固有约束（role alternation、token 限制、provider schema 差异）导致的必然设计。

4. **预算控制是必需品**：即使是最信任模型的 OpenCode，也有 `agent.steps` 配置。没有任何框架允许无限循环。这说明"模型可能陷入死循环"是所有 Agent 开发者的共识。

### 8.3 最重要的差异发现

1. **对模型错误的态度是最大的分水岭**：nanobot 选择"不入历史"（最谨慎），OpenClaw 选择"分类恢复"（最全面），Hermes 选择"重试 + fallback"（最务实），OpenCode 选择"信任 SDK"（最信任）。这个选择直接影响框架的稳定性上限。

2. **并发模型决定了框架的能力天花板**：Hermes 的线程模型支持工具级并发，OpenClaw 的双层队列支持会话级并发，nanobot 和 OpenCode 都是串行。在"让 Agent 同时做多件事"这个方向上，Hermes 走得最远。

3. **OpenClaw 的"分层恢复"是生产级 Agent 的分界线**：compaction → 截断 → Profile 轮换 → thinking 降级 → model fallback，这条恢复链的每一层都是"前一层失败后的最后手段"。个人助手和 IDE 插件不需要这个，但 7×24 运行的网关服务必须有。

## 9. 如果我要构建自己的编排循环，应该怎么选

| 我要做什么 | 推荐借鉴 | 原因 |
|-----------|---------|------|
| 需要 7×24 运行的网关 Agent | OpenClaw 的分层恢复 + 双层队列 | 生产级稳定性要求每层都有独立恢复策略 |
| CLI 工具 / 开发者助手 | Hermes 的预算控制 + 可中断 API 调用 | 用户会按 Ctrl+C，必须能立即响应 |
| 个人助手 / 聊天机器人 | nanobot 的两层分离 + 纯函数内循环 | 简单可靠，内循环可独立测试 |
| IDE 集成 Agent | OpenCode 的流式事件 + doom loop 检测 | 流式输出是 IDE 场景的刚需 |
| 需要并行工具执行 | Hermes 的 ThreadPoolExecutor + 白名单 | 唯一支持工具级并发的方案 |
| 需要支持多种 LLM Provider | Hermes 的消息清理 + nanobot 的错误隔离 | Provider 差异需要防御性处理 |

**最值得直接复用的设计**：
1. Hermes 的 `IterationBudget` + `_budget_grace_call` — 预算耗尽时的优雅收尾
2. nanobot 的 `finish_reason=="error"` → 不入历史 — 4 行代码挡住整类事故
3. OpenClaw 的恢复策略按成本排序 — compaction < 截断 < 轮换 < 降级 < fallback
4. OpenCode 的 `DOOM_LOOP_THRESHOLD` — 检测模型陷入死循环
5. Hermes 的 `_should_parallelize_tool_batch` — 保守但零误伤的并发决策
6. nanobot 的 `_run_agent_loop` 纯函数 — 内循环不读不写 session，可独立测试
