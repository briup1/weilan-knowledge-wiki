# 需求 0001：企业内部 Agent 测试平台 MVP

> 本文是当前讨论阶段的唯一事实来源。只记录需求、边界和已形成的共识，不记录未经批准的实现方案。关键方案将在需求边界明确后另行设计；在需求与方案均获批准前，不开始开发。项目术语统一见 [`CONTEXT.md`](../../../CONTEXT.md)。

## 1. 文档治理

### 1.1 记录规则

- 每轮讨论后更新本文，不依赖聊天记录保存共识。
- 用户明确认可的结论标为“已确认”。
- 尚未确认但为推进讨论而提出的判断标为“暂定假设”。
- 无明确答案或存在分歧的事项进入“未决问题”。
- 明确不采用的方向进入“已否决方向”，避免后续反复讨论。
- 影响范围大、难以逆转或存在明显取舍的结论进入“决策记录”。
- 对已确认结论的修改必须保留在“变更记录”中。

### 1.2 状态定义

```text
draft（持续澄清）
  ↓ 所有必要维度有明确结论
reviewing（整体复核）
  ↓ 需求方明确批准
approved（需求冻结）
  ↓ 另行完成并批准方案设计

```

### 1.3 讨论完成条件

以下条件全部满足后，才能结束讨论阶段：

- 必要维度全部为“已确认”或“明确延期”，不存在未标记假设。
- MVP 必做、非目标以及与外部系统的责任边界清晰。
- 关键术语含义一致。
- 高影响风险有明确处置结论。
- 未决问题清零，或有经需求方批准的延期理由和责任归属。
- 需求方完成整体复核并明确批准。

### 1.4 讨论章程（已确认）

#### 原则

1. **宏观优先**：先确认平台边界、模块划分、模块职责、主流程和 MVP 取舍，再讨论字段、算法、指标阈值及运行参数。
2. **一次只讨论一个层级**：当前处于模块级讨论，不混入接口 Schema、运行次数、评分阈值、误报率等实现或验收细节。
3. **先职责、后方案**：先回答模块解决什么问题、拥有什么责任，再比较 Langfuse、DeepEval 等实现选择。
4. **先边界、后能力清单**：先划清平台与 Agent、Langfuse、CI/CD、发布平台等外部系统的职责，再决定平台内部能力。
5. **MVP 与长期目标分开**：每个模块都要标明 MVP 必做、明确延期和长期方向，不能用长期完整性扩大首期范围。
6. **每轮落盘**：每轮只把用户明确认可的结论标为“已确认”；其余分别进入假设、未决问题或已否决方向。
7. **细节不丢失但暂时冻结**：提前出现的细节问题进入“细节问题池”，待宏观阶段结束后按模块逐项讨论。

#### 讨论顺序

```text
平台定位与外部边界
  ↓
宏观模块划分
  ↓
模块职责与模块间主流程
  ↓
MVP 取舍与分阶段路线
  ↓ 宏观方案经需求方确认
逐模块讨论契约、数据、规则与指标细节
  ↓
整体复核与需求批准
```

#### 单个模块的固定讨论模板

每个一级模块只回答以下五类宏观问题：

1. **目标**：该模块解决什么核心问题？
2. **职责**：该模块必须负责什么，不负责什么？
3. **协作边界**：它从谁接收什么、向谁交付什么；哪些责任属于外部系统？
4. **MVP 取舍**：首期必须具备什么，哪些能力明确延期？
5. **风险与依赖**：有哪些会影响模块存在方式或平台边界的关键约束？

#### 宏观阶段退出条件

以下条件全部满足后，才进入细节讨论：

- 一级模块地图获得需求方批准。
- 每个模块的目标、职责和非职责明确。
- 平台与主要外部系统的责任边界明确。
- 模块间主流程和关键交付物明确。
- 每个模块的 MVP 必做与延期项明确。
- 分阶段路线获得需求方批准。
- 剩余细节问题已按所属模块归档，不再反向改变宏观边界；若会改变边界，则继续留在宏观阶段处理。

## 2. 需求重定义

### 原始诉求

建设企业内部 MVP 版 Agent 测试程序，重点解决三类问题：不同 Agent 的便捷接入、基于 Agent 场景和角色自动生成测试用例，以及 Agent 变更后的回归与灰度验证。

### 最终目标

建立一个可持续积累测试资产、发现 Agent 能力退化并为变更提供质量证据的企业内部平台，使 Agent 团队能够在发布前后判断“新版本是否仍然可靠”。

### 当前异议

“对接所有 Agent”暂不能直接作为 MVP 验收口径。它更适合作为长期架构约束；MVP 应通过代表性 Agent 验证接入边界是否可扩展。需要进一步确认“所有 Agent”的实际范围和差异类型。

“灰度测试”可能涉及发布流量调度、线上质量评估和回滚三个不同职责。测试平台是否直接控制流量尚未明确，需与企业现有发布系统划界。

### 重定义后的需求

平台应以框架中立的方式接入目标范围内的 Agent，形成经过人工治理的版本化测试资产，在 Agent 发生变更时执行可比较、可追溯的回归验证，并为发布门禁或灰度决策提供质量证据。

### 当前产品定位（已确认）

MVP 首先服务 Agent 开发者，优先解决 Agent 发生变更后无法可靠发现能力退化的问题。首批以对话问答 Agent 和工具执行 Agent 为代表性对象；第一阶段先证明“可靠发现退化”，自动生成用例和通用接入是支撑该目标的手段，而不是独立追求功能数量。

Agent 开发者对正式回归场景和最终质量结论承担主要责任。平台不是替代已有自动测试脚本，而是补齐跨版本退化识别和重复运行结论稳定性。首批优先防止两类高风险失败：关键要求遗漏、工具调用错误。

### 宏观模块地图（已确认作为讨论底稿）

```text
Agent 测试平台
├─ 1. Agent 接入与观测
│  ├─ Agent 调用
│  └─ 内部 Trace / Event 采集
├─ 2. 测试资产管理
│  ├─ 场景与预期
│  ├─ 自动生成
│  └─ 人工审核与版本
├─ 3. 测试执行
│  ├─ 单例调试
│  ├─ 离线回归
│  └─ Shadow / Canary 评测
├─ 4. 评测引擎
│  ├─ 最终回答评测
│  ├─ 工具与过程评测
│  └─ 稳定性与版本对比
├─ 5. 结果与决策
│  ├─ 报告和问题定位
│  ├─ 发布建议
│  └─ CI / 发布系统衔接
└─ 6. 平台治理
   ├─ 权限与安全
   ├─ 成本与审计
   └─ 配置及外部系统集成
```

该地图当前用于组织讨论，表示六个待确认的职责域，不代表六个部署服务、六个代码模块或最终页面结构。后续可以在不丢失职责的前提下合并、更名或调整层级。

### 模块级共识

#### 1. Agent 接入与观测（已确认）

**目标**：屏蔽不同 Agent 的调用与观测差异，为测试执行提供可识别版本、可关联 Trace 的统一执行证据。

**职责**：

- 识别被测 Agent 及其版本。
- 发起或承接一次 Agent 交互。
- 关联最终回答、工具调用和内部 Trace。
- 检查评测所需证据是否齐全，并向测试执行与评测引擎提供统一证据视图。
- 声明每个 Agent 当前支持的评测能力。

**明确非职责**：

- 不实现 Agent 自身业务逻辑和编排。
- 不决定执行哪些测试场景，也不判断测试是否通过。
- 不负责发布、流量切换或回滚。
- 不建设第二套通用 Trace 采集、存储、检索和观测后台。

**分级接入**：

```text
基础接入：可调用 + 可识别版本
  └─ 支持端到端黑盒评测

增强接入：基础接入 + 内部 Trace / Event
  └─ 支持组件级评测和精确问题定位
```

**与 Langfuse 的边界**：

```text
Agent → Langfuse
  └─ 采集、存储和检索原始 Trace / Span / 模型与工具事件

Agent 测试平台
  ├─ 关联 Test Run 与 Langfuse Trace
  ├─ 校验评测证据完整性
  ├─ 提取统一评测证据视图
  └─ 不复制原始 Trace 数据面
```

**MVP 取舍**：

- MVP 确定使用 Langfuse 负责 Trace 数据面。
- 同时支持基础接入和增强接入；缺少内部事件的 Agent 只能获得端到端黑盒评测能力。
- 不要求所有 Agent 使用相同业务框架，但增强接入必须能把内部事件送入 Langfuse。
- 其他 Trace Provider、多 Trace 后端并存和 Trace 平台自建明确延期。

#### 2. 测试资产管理（已确认）

**目标**：将 Agent 能力描述、业务要求、历史缺陷和真实 Trace 转化为可审核、可版本化、可重复执行的测试资产。

**职责**：

- 管理测试场景、预期回答、预期工具过程及适用范围。
- 根据 Agent 职责、业务资料、历史失败和 Langfuse Trace 生成候选用例。
- 支持人工创建、修改、审核、正式发布和停用测试资产。
- 管理资产版本、变更来源及与需求、缺陷、Trace、Agent 能力的关联。
- 将正式场景组织为可执行的 Benchmark Set。

**明确非职责**：

- 不采集或保存原始 Trace。
- 不调用 Agent 执行测试，也不计算评分或判断退化。
- 不替代业务方定义正确的业务规则。
- 不决定 Agent 是否可以发布。

**资产治理闭环**：

```text
Agent 信息 / 业务要求 / 历史缺陷 / Langfuse Trace
                         ↓
                      候选资产
                         ↓ 人工审核
                    正式回归资产
                         ↓ 业务变化或失效
                      停用资产
```

**治理原则**：

- 自动生成只负责降低用例建设成本，未经人工确认的候选资产不得进入正式回归集。
- Agent 开发者对正式测试资产负责；高风险业务场景可以邀请业务专家协作审核。
- Langfuse Trace 可以作为资产生成和追溯来源；平台只保存关联，不复制原始 Trace。

**MVP 取舍**：

- 迁移并演进 `eyun_assist_bot` 的旧 Benchmark Schema。
- 支持人工创建和编辑、候选用例自动生成、人工审核转正式、基本版本管理、Benchmark Set 组织及来源与变更记录。
- 未经人工审核自动入库、多级复杂审批流、企业级测试资产市场、根据线上效果自动修改 Golden Dataset，以及自动判断业务规则本身是否正确，均明确延期。

#### 3. 测试执行（讨论中）

**已确认触发边界**：

```text
MVP：仅人工触发测试执行
后续：CI/CD 触发、线上观测触发
```

MVP 不接收 CI/CD 或线上观测自动触发；人工触发通过页面、命令还是 API 实现，属于后续细节问题。测试执行模块的其他职责、非职责、执行方式和环境边界仍待模块级确认。

## 8. MVP 范围与非目标

### 已确认必做

- 服务 Agent 开发者，以可靠发现 Agent 变更后的能力退化为第一阶段核心价值。
- 首批覆盖对话问答 Agent 和工具执行 Agent。
- 支持端到端评估、组件级评估和单例调试三种工作方式。
- 支持采集 Agent 内部执行事件，以定位回答或工具执行退化。
- 支持不同 Agent 的可扩展接入方向。
- 能基于 Agent 信息生成候选测试用例。
- 能沉淀历史场景并在 Agent 变更后执行回归。
- 新功能场景能进入后续稳定性验证范围。

### 尚未确认

- 首期 Agent 数量和类型。
- 何时从发布建议升级为强制 CI 门禁；MVP 第一阶段不直接强制门禁。
- CI/CD 触发和线上观测触发在 MVP 后增加。
- 线上 Shadow、Canary 流量控制和自动回滚在 MVP 后讨论。
- 是否自建 Trace、数据集管理和人工审核界面。
- DeepEval 是否作为评估器库引入；当前只确认三种工作方式，不确认具体库。

### 已确认不做

- 在需求边界和方案未获批准前进行开发。
- MVP 不接收 CI/CD 或线上观测自动触发。

详细代码证据、资产分类、历史结果与缺口见 [`existing-assets-analysis.md`](existing-assets-analysis.md)。DeepEval 与 Langfuse 的官方能力及接入成本比较见 [`deepeval-vs-langfuse.md`](deepeval-vs-langfuse.md)。

### 已核实资产

| 资产 | 位置 | 已有能力 | 当前限制 |
|---|---|---|---|
| Session 级评测闭环 | `origin/feature/agent-multi-session-evaluation-management` | 多轮真实 Agent 旁路执行、Toolflow/回答双轨评估、多 Run 稳定性、报告和 Web 控制台 | 绑定 eyun DeepAgents 与内部环境；无自动用例生成和跨 Agent 接入契约 |

| 多模型黑盒评测 | `origin/task/model-eval-scripts` | 28 条单轮用例、HTTP/SSE 调用、多轮次稳定性、时延和可选 Token 统计 | 规则高度业务化、只测首轮、并非 Session 回归闭环 |

### 对当前需求的影响

- 新项目不是从零建设评测闭环，而是把单 Agent、文件级原型抽象为可治理、可扩展的企业内部产品。
- 旧资产已验证多次 Run 能揭示工具流程波动和关键要求遗漏，与当前首要目标一致。
- 旧 Collector 直接绑定 `create_deep_agent()`，其 `adapter.py` 也只是评测格式转换，不能视为已解决通用 Agent 接入。
- 旧系统在 Agent 或 Expected 变化后要求 Reset Run，缺少 Baseline Agent 与 Candidate Agent 的跨版本并存比较。
- 历史代码包含硬编码测试身份和访问凭证，且已跟踪环境文件中存在多类真实密钥变量；具体值不进入本文，Git 历史中的全部真实凭证均需确认失效或轮换。
- 历史资产 Lint 已发现一条场景的 Session Run 与 Stability 汇总不一致，迁移前必须治理，不能直接升为正式 Golden Dataset。

### 继承分类（待确认）

- **已确认继承领域设计**：Scenario、Expected Toolflow、Expected Answer、Real Session、Run、Stability、Benchmark Set；过程与结果分离；`official/review/skipped`；Asset Lint。具体字段在方案阶段演进，不承诺原样兼容。
- **待设计后复用**：旁路采集、轨迹匹配、LLM Judge、批量 Runner、Web 控制台、Dashboard、HTTP/SSE 黑盒脚本。
- **仅作历史证据**：业务 Matcher、固定身份和环境、旧运行结果、以特定模型输出为满分参照的评分逻辑。
